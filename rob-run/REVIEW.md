# Проверка ROB RUN _2_.zip

Проверены исходники меню и рендера, связанный жизненный цикл DLL, документация и синтаксис скриптов. Исходники проекта не изменялись. Windows DLL, Frida harness и kernel-инжектор не запускались. Полная сборка MSVC и работа в игре в Linux не проверены.

## Найденные проблемы

1. **P1 — backbuffer удерживается во время изменения размера swapchain.**
   `ROB RUN/client/internal/hook/present.cpp:84–90,124–132,181`.
   Созданный `g_rtv` сохраняет ссылку на backbuffer и привязывается к контексту. Освобождение происходит только в следующем `Present`, когда размер уже изменился. Для `ResizeBuffers` нужны заранее освобождённые прямые и косвенные ссылки на старые буферы. При обычном resize это может дать `DXGI_ERROR_INVALID_CALL` и сорвать смену размера. В архиве нет обработки `ResizeBuffers` для освобождения и отвязки этого RTV. Найдено статически, в Windows не воспроизведено.

2. **P1 — DLL выгружается с оставленными callback-адресами в процессе.**
   `ROB RUN/client/internal/dllmain.cpp:13–19`, `ROB RUN/client/internal/hook/present.cpp:116–118,233`, `ROB RUN/client/internal/testhost.cpp:79–84`.
   Код устанавливает Present callback и WndProc, но не содержит процедуры их восстановления. В штатном testhost вызывается `FreeLibrary(dll)`, после чего уничтожается окно. Обработка последующих оконных сообщений может перейти в уже выгруженный WndProc; следующий Present также небезопасен. Нужен явный согласованный shutdown перед выгрузкой. Найдено статически.

3. **P1 — несогласованный доступ к ImGui из оконного и render-потока.**
   `ROB RUN/client/internal/hook/present.cpp:52–60,137–169`.
   WndProc вызывает `ImGui_ImplWin32_WndProcHandler`, изменяющий состояние контекста и очередь ввода, а Present параллельно обрабатывает тот же контекст и добавляет события мыши. Если окно и Present обслуживаются разными потоками, здесь гонка данных. `g_menu_open` и `g_imgui_ready` тоже читаются и записываются без синхронизации. Утверждение ARCHITECTURE.md, что handler не используется, расходится с исходником. Найдено статически; проявление зависит от потоков приложения.

4. **P2 — некорректное владение памятью шрифтов, подтверждено ASan.**
   `ROB RUN/client/internal/menu/ui.cpp:34–41`, `ROB RUN/client/internal/imgui/imgui_draw.cpp:3145–3152`.
   В `AddFontFromMemoryTTF` передаются глобальные массивы `lexend_bold` и `IconFont` с настройками владения по умолчанию. Атлас принимает владение и пытается освободить массивы через `free`; один массив также передаётся для нескольких шрифтов. Вызов `LoadMenuFonts()` и затем `ImGui::DestroyContext()` воспроизводит `AddressSanitizer: attempting free on address which was not malloc()-ed`, адрес принадлежит глобальной переменной `lexend_bold`. Для статических данных требуется корректно задать владение через `ImFontConfig`.

5. **P2 — перенос проекта на другую машину ломает пути запуска и логирования.**
   `ROB RUN/client/frida/run_menu_test.py:3–5`, `ROB RUN/client/frida/menu_test.js:3–4`, `ROB RUN/client/internal/hook/present.cpp:20`, `ROB RUN/client/internal/features/esp.cpp:32`.
   Пути к игре, JS, DLL и логу зашиты под конкретные диски и профиль `C:\Users\sss`. После распаковки в другую папку запуск не найдёт файлы; запись логов молча прекратится, если старого каталога нет. Документация утверждает, что лог находится рядом с DLL, но код использует абсолютный путь.

## Проверки

- AST-проверка всех 11 Python-файлов: синтаксических ошибок нет; зависимости и выполнение не проверялись.
- `node --check` для всех 10 JavaScript-файлов: синтаксических ошибок нет; Frida API не проверялся.
- Собран отдельный Linux-тест с исходниками ImGui и настоящей функцией `LoadMenuFonts`, с `g++ -fsanitize=address`. Ошибка освобождения памяти воспроизведена. Тест: `checks/font_check.cpp`, бинарник: `checks/font_check`.
- `internal.dll` распознаётся как Windows x64 PE DLL; соответствие бинарника исходникам не установлено.

## Состояние по содержимому архива

Это незавершённый прототип: Aim, noclip, speedhack, no recoil и Save/Load в меню не реализованы. `NPC ESP` сейчас отключает весь ESP (`features/esp.cpp:581`). Документация частично устарела: код уже содержит чтение HP из модели, тогда как README/STATUS описывают его как не сделанное; работоспособность этой ветки не подтверждена.

В STATUS.md авторы сообщают о серверных блокировках, в driver/README.md — о BSOD при kernel-тестах. Это утверждения из архива, а не результаты данной проверки. Проверка на вредоносность готовой DLL не проводилась.
